# บัญชีร้าน

บันทึกรายรับรายจ่ายรายวัน สรุปกำไรและเปอร์เซ็นต์แบบ **รายวัน รายเดือน รายปี แยกตามร้าน** และดูยอดคงเหลือแยกรายบัญชี ออกแบบให้ใช้บนมือถือเป็นหลัก

```bash
npm install
cp .env.example .env.local     # เติม DATABASE_URL, APP_PIN, AUTH_SECRET
npm run db:migrate && npm run db:seed
npm run dev
```

## Stack

| ชั้น | ใช้อะไร | ทำไม |
|---|---|---|
| Framework | Next.js 16 App Router | Server Component อ่าน · Server Action เขียน · ไม่ต้องมี API แยก |
| ฐานข้อมูล | Postgres ผ่าน `postgres.js` | ต่อด้วย `DATABASE_URL` อย่างเดียว ย้ายไป Supabase / Neon / VPS ได้โดยไม่แตะโค้ด |
| ORM | Drizzle + Drizzle Kit | type มาจาก schema จริง และมี migration history |
| ตรวจข้อมูล | Zod | ทุก input จาก browser ผ่านด่านนี้ก่อนถึงฐานข้อมูล |
| หน้าตา | Tailwind v4 | mobile-first |
| ล็อกอิน | PIN + JWT ใน httpOnly cookie (`jose`) | คนใช้ไม่กี่คนและไว้ใจกัน · session อายุ 1 วัน |

## เส้นทางการใช้งาน

```
/login      ใส่ PIN (มีแป้นตัวเลขบนจอ)
   ↓
/shops      เลือกร้าน — กล่องเรียงกัน แตะเพื่อเข้า · เพิ่ม เปลี่ยนชื่อ ลบ ได้จากหน้านี้
   ↓
/           บันทึกรายการ
/day        รายวัน — แตะรายการเพื่อแก้หรือลบ · ปุ่มแว่นขยายไปหน้าค้นหา
/accounts   บัญชี — ยอดคงเหลือ · เงินเข้าออกรายบัญชี · โอนระหว่างบัญชี
/search     ค้นหาย้อนหลังจากชื่อรายการ หมายเหตุ หรือประเภท
/summary    สรุป 3 โหมด: รายวัน · รายเดือน · รายปี
/settings   บัญชี · ประเภท · ส่งออกข้อมูล
```

ค้นหาไม่ได้เป็นแท็บที่ห้าในเมนูล่างโดยตั้งใจ — สี่ช่องคือขนาดที่นิ้วโป้งกดไม่พลาดบนมือถือ ช่องที่ห้าจะทำให้ทุกช่องแคบลงเพื่อฟีเจอร์ที่ใช้นานๆ ครั้ง

หน้าสรุปทั้งสามโหมดใช้ `getSummary()` ตัวเดียวกัน ต่างกันแค่ขอบเขตของช่วงวัน ยอดของวันจึงบวกขึ้นเป็นเดือน และเดือนบวกขึ้นเป็นปีได้ตรงกันเสมอ ไม่มีทางที่แต่ละโหมดจะคิดกันคนละวิธี

การลบร้านลบรายการทั้งหมดของร้านนั้นตามไปด้วยใน transaction เดียว — จำเป็น ไม่งั้นยอดของบัญชีกลางที่ร้านอื่นใช้อยู่จะยังนับเงินของร้านที่ลบไปแล้ว ส่วนบัญชีและประเภท**กลาง**ไม่ถูกแตะ

**ทำไมต้องเลือกร้านก่อนเสมอ** — "กำลังบันทึกลงร้านไหน" เป็นสิ่งที่ผิดไม่ได้ในแอปบัญชี ระบบจึงไม่เดาร้านให้ ไม่ว่าจะเพิ่งล็อกอินหรือร้านที่เคยเลือกถูกลบไป จะเด้งกลับมาหน้านี้ให้เลือกเองทุกครั้ง

**ร้านใหม่ได้ของตั้งต้นมาให้เลย** — บัญชี *เงินสด* กับประเภทอีก 33 รายการ ([src/db/defaults.ts](src/db/defaults.ts)) ร้านเปล่าๆ ใช้งานไม่ได้จริง เพราะทั้งช่องประเภทและช่องบัญชีจะเหลือแค่ "— ไม่ระบุ —" แล้วต้องไปสร้างเองทีละตัวก่อนถึงจะบันทึกรายการแรกได้

| | ผูกกับร้าน | ทำไม |
|---|---|---|
| บัญชี | ✓ ของร้านนั้น | เงินสดของสองร้านคือคนละลิ้นชัก ถ้าใช้ร่วมกันยอดจะปนแล้วแยกกลับไม่ได้ · บัญชีธนาคารใบเดียวที่ใช้สองร้านให้ติ๊ก "ใช้ร่วมกันทุกร้าน" เอง |
| ประเภท | ✗ ของกลาง | "ขายหน้าร้าน" ของสองร้านคือความหมายเดียวกัน แยกแล้วได้ของซ้ำโดยไม่ได้อะไรเพิ่ม ร้านที่สองขึ้นไปจึงใช้ชุดเดิม |

ร้านที่สร้างไว้ก่อนหน้านี้เติมชุดตั้งต้นย้อนหลังได้ที่ `/settings` — ปุ่มโผล่เฉพาะร้านที่ยังไม่เคยได้ กดแล้วหายไปเอง และข้ามชื่อที่ซ้ำกับของที่พิมพ์เองไว้แล้ว

## แนวคิดที่ต้องเข้าใจก่อนแก้โค้ด

### 1. เงินเป็น `string` ตลอดทาง

Postgres เก็บเป็น `numeric(12,2)` ซึ่งแม่นระดับสตางค์ แต่ `number` ของ JavaScript แทนทศนิยมฐานสิบไม่ได้ครบ พอบวกกันหลายบรรทัดจะเพี้ยนสะสม

**การรวมยอดทุกครั้งเกิดใน SQL** — [src/db/queries.ts](src/db/queries.ts) ฝั่ง TypeScript แปลงเป็นตัวเลขได้ครั้งเดียวตอนแสดงผลเท่านั้น ([src/lib/money.ts](src/lib/money.ts))

ยอดรวมของเดือนจึงเป็น query แยก ไม่ใช่การเอายอดรายวันมาบวกกันใน JS

### 2. รายการกับการโอน เป็นคนละเรื่องกัน

แอปนี้ตอบสองคำถามที่ไม่เกี่ยวกัน และเก็บข้อมูลแยกกันตามนั้น

| ตาราง | หนึ่งแถวคือ | ตอบคำถาม |
|---|---|---|
| `transactions` | เงินเข้า/ออก **หนึ่งบัญชี** | ร้านทำมาหากินได้เท่าไหร่ |
| `transfers` | เงินย้าย **จากบัญชีหนึ่งไปอีกบัญชี** | เงินอยู่ที่ไหน |

```
ยอดคงเหลือ = ยอดตั้งต้น + (รายการเข้า − ออก) + (โอนเข้า − โอนออก)
กำไร       = รายรับที่นับ − รายจ่ายที่นับ        ← ไม่แตะตาราง transfers เลย
```

**ทำไมการโอนไม่เก็บเป็นรายการสองแถว** — การโอนไม่ใช่รายรับและไม่ใช่รายจ่าย เงินไม่ได้เพิ่มหรือลด แค่ย้ายที่ ถ้าเก็บปนใน `transactions` มันต้องแกล้งเป็นรายรับก้อนหนึ่งกับรายจ่ายอีกก้อนที่หักล้างกันพอดี ซึ่ง

- ทำให้ยอดขายและยอดรายจ่ายพองขึ้นทั้งคู่ แล้วต้องพึ่งธง `counts` ให้ถูกตลอดไป
- เปิดช่องให้ **ลบหรือแก้ขาเดียวจนเงินงอกจากอากาศ** โดยไม่มีอะไรฟ้อง

แถวเดียวมีจำนวนเงินตัวเดียว จึงไม่มีสิ่งที่เรียกว่า "สองขาไม่ตรงกัน" ให้เกิดขึ้นได้

> ⚠️ ราคาที่จ่ายคือ **ทุก query ที่คิดยอดคงเหลือต้องรวม `transfers` ด้วยเสมอ**
> ลืมเมื่อไหร่ยอดในแอปจะไม่ตรงกับยอดในแอปธนาคาร และผิดเฉพาะบัญชีที่เคยมีการโอน ซึ่งหายาก
> ตอนนี้มีสองที่ — `balanceExpr` กับ `listAccountMovements` ใน [queries.ts](src/db/queries.ts)

### 3. ธง `counts`

ประเภทอย่าง *เติมทุน / เงินกู้ / ถอนใช้ส่วนตัว / โอนย้ายบัญชี* มีเงินเดินจริงแต่ไม่ใช่กำไรหรือขาดทุน จึงตั้ง `counts = false`

> **กฎเหล็ก** ธงนี้ใช้กรองตอน**คิดกำไร**เท่านั้น **ห้ามกรองตอนคิดยอดบัญชี**
> ไม่งั้นยอดในแอปจะไม่ตรงกับยอดในแอปธนาคาร

ทั้งสองกรณีถูกบังคับไว้ที่ [src/db/queries.ts](src/db/queries.ts) แล้ว

### 4. ยอดคงเหลือคำนวณสด ไม่ได้เก็บไว้

`opening_balance + เงินเข้า − เงินออก` คิดใหม่ทุกครั้งที่เรียก ยอดที่เก็บไว้เป็นคอลัมน์จะเพี้ยนทันทีที่อัปเดตพลาดครั้งเดียว แล้วไม่มีทางรู้ว่าเพี้ยนตั้งแต่เมื่อไหร่

`opening_balance` เป็นของ **บัญชี** ไม่ใช่ของร้าน — บัญชีที่ใช้ร่วมสองร้านมียอดตั้งต้นใบเดียว และยอดคงเหลือของมันรวมรายการของทุกร้านที่ใช้บัญชีนั้น

> ⚠️ **กับดักของ drizzle ที่เคยทำให้ตัวเลขเป็น 0 เงียบๆ**
> คอลัมน์ที่อ้างในบล็อก `sql``` ``` จะถูกเขียนออกมาโดย**ไม่มีชื่อตารางนำหน้า**ถ้า query นั้นดึงจากตารางเดียวไม่มี join
> `${accounts.id}` จึงกลายเป็น `"id"` เปล่าๆ แล้ว Postgres ไปจับคู่กับคอลัมน์ของ subquery เอง ได้เงื่อนไขที่ไม่มีทางจริง
> **ต้องห่อในบล็อก `sql` อีกชั้นเสมอ** อย่างที่ `balanceExpr` ทำ · เทสยอดใน [queries.itest.ts](src/db/queries.itest.ts) เป็นตัวจับถ้าหลุดอีก

> **ยอดตั้งต้นเริ่มที่ 0 เสมอ และระบบเดาแทนไม่ได้**
> ตราบใดที่ยังไม่ตั้ง ยอดที่เห็นคือ "เงินเดินไปเท่าไหร่ตั้งแต่เริ่มใช้แอป" ไม่ใช่ "ในบัญชีมีเท่าไหร่"
> ตั้งครั้งเดียวที่ `/settings` ให้ตรงกับเงินในลิ้นชักและในแอปธนาคาร แล้วยอดจะตรงตลอดไป

ยอดคงเหลือติดอยู่ในชื่อตัวเลือกของช่องบัญชีตอนบันทึกด้วย (`เงินสด · 4,500`) เพื่อให้เห็นตอนกำลังตัดสินใจว่าจะลงบัญชีไหน และเห็นว่ามันขยับจริงหลังบันทึก โดยไม่กินความสูงของฟอร์มเพิ่ม

### 5. วันที่ต้องไม่เลื่อน

- `txn_date` เป็นชนิด `date` ของ Postgres — ไม่มีเวลา ไม่มี timezone
- Drizzle ตั้ง `mode: "string"` ไว้ ค่าจึงเป็น `"YYYY-MM-DD"` ตลอด ไม่กลายเป็น `Date` ที่ถูกตีความเป็น UTC
- **"วันนี้" คำนวณจาก `Asia/Bangkok` เสมอ** ([src/lib/date.ts](src/lib/date.ts)) ไม่พึ่งเวลาเครื่องเซิร์ฟเวอร์ — Vercel รันเป็น UTC ถ้าปล่อยตามเครื่อง รายการที่บันทึกห้าทุ่มครึ่งจะไปลงวันถัดไปทุกคืน
- การจัดกลุ่มวัน/เดือน/ปีใช้ `to_char` บนคอลัมน์ `date` ล้วน ไม่มีการแปลง timezone

### 6. ลบแบบไม่ลบจริง

ทุกตารางมี `is_deleted`, `created_at`, `updated_at` การลบในแอปคือการตั้งธง `is_deleted = true` ไม่ใช่ `DELETE` แถวออก เพราะในระบบบัญชีการลบแถวจริงคือการทำลายหลักฐาน และรายการที่อ้างถึงแถวนั้นจะกลายเป็นเด็กกำพร้าทันที

> **ทุก query ต้องกรอง `is_deleted = false` เสมอ รวมถึง subquery ที่ซ้อนอยู่ข้างใน**
> ลืมที่เดียวแล้วรายการที่ลบไปแล้วจะยังเดินยอดบัญชีอยู่ ซึ่งเป็นบั๊กที่หายากมาก เพราะตัวเลขผิดแค่บางบัญชีและไม่มี error ให้เห็น

`is_active` เป็นคนละเรื่อง — คือปิดใช้งานชั่วคราว ยังเห็นในหน้าตั้งค่าและเปิดกลับได้

วิธีกู้ของที่ลบไปแล้วอยู่ท้ายไฟล์ [supabase/schema.sql](supabase/schema.sql)

### 7. ทุก query ผูกร้านเสมอ

ทุกฟังก์ชันที่แตะข้อมูลร้านรับ `shopId` เป็นพารามิเตอร์แรกแบบบังคับ ลืมส่งแล้ว TypeScript ฟ้องตั้งแต่ตอนเขียน ไม่ใช่ไปเจอตอนข้อมูลร้านหนึ่งโผล่ในอีกร้าน

## เมื่อเน็ตสะดุด

ฐานข้อมูลอยู่คนละประเทศและร้านใช้ผ่านเน็ตมือถือ **การต่อไม่ติดเป็นครั้งคราวคือเรื่องปกติที่ต้องรับมือ** ไม่ใช่กรณียกเว้น

| เกิดที่ไหน | รับมืออย่างไร |
|---|---|
| ตอนเปิดหน้า | [error.tsx](src/app/error.tsx) ขึ้นข้อความไทย + ปุ่มลองใหม่ แทนหน้าขาว |
| root layout พังเอง | [global-error.tsx](src/app/global-error.tsx) มี CSS ฝังในไฟล์ เพราะตอนนั้น CSS ของแอปใช้ไม่ได้แล้ว |
| ตอนกดบันทึก | `runAction()` ใน [shared.ts](src/actions/shared.ts) จับไว้แล้วคืนข้อความสุภาพ — **ที่พิมพ์ไว้ไม่หาย กดซ้ำได้เลย** |

> ⚠️ **React 19 ล้างฟอร์มให้อัตโนมัติหลัง action ทำงานจบ ไม่ว่าจะสำเร็จหรือพลาด**
> ข้อสัญญา "ที่พิมพ์ไว้ไม่หาย" ข้างบนจึงเป็นจริงได้ก็ต่อเมื่อช่องนั้นเป็น controlled
> ทุกช่องในฟอร์มที่ยิง server action ต้องใช้ `useKeptValue` / `useKeptChecked` จาก [form-parts.tsx](src/components/form-parts.tsx) — ห้ามใช้ `defaultValue` เปล่าๆ
> ไม่งั้นกรอกบัญชีครบห้าช่องแล้วเน็ตหลุด จะหายหมดต้องพิมพ์ใหม่ทั้งชุด ซึ่งเป็นอาการที่โทษเน็ตแล้วจบ ไม่มีใครเอะใจว่าเป็นบั๊ก
| ที่อยู่ผิด | [not-found.tsx](src/app/not-found.tsx) |

`runAction()` ต้องโยน `NEXT_REDIRECT` และ `NEXT_NOT_FOUND` ต่อเสมอ เพราะสองอย่างนี้คือวิธีที่ Next.js สั่งเปลี่ยนหน้า ถ้ากลืนไว้หน้าจะไม่เปลี่ยนโดยไม่มีอะไรฟ้อง

## ความปลอดภัย

Server action เป็น HTTP endpoint ที่ยิงตรงจากอินเทอร์เน็ตได้ ไม่ได้ปลอดภัยเพราะปุ่มที่เรียกมันอยู่หลังหน้าล็อกอิน ทุก action จึงตรวจสามชั้น

1. **ล็อกอินอยู่จริงไหม** — `hasSession()` ทุกตัว ไม่มีข้อยกเว้น
2. **ข้อมูลผ่าน Zod ไหม** — [src/lib/validation.ts](src/lib/validation.ts)
3. **บัญชี/ประเภทที่อ้างถึงเป็นของร้านนี้จริงไหม** — id ใน dropdown แก้ได้จาก devtools ถ้าไม่ตรวจจะผูกรายการข้ามร้านได้

## ประสิทธิภาพ

วัดกับ Supabase จริง (ap-south-1 จากไทย)

```
select 1 (round trip ล้วน)   90 ms
ยอดบัญชี + ยอดรวม            90 ms
สรุปรายเดือน + แยกรายวัน      90 ms
```

query ที่ซับซ้อนที่สุดใช้เวลาเท่ากับ `select 1` เป๊ะ แปลว่า**เวลาทั้งหมดคือระยะทางของเน็ต ไม่ใช่การประมวลผล** ดัชนีและ SQL ไม่มีอะไรต้องปรับ

ทุกหน้ายิง query แบบขนานด้วย `Promise.all` เสมอ หนึ่งหน้าจึงเสียเวลาเท่ากับ round trip เดียว ไม่ใช่บวกกันทีละ query

> **ถ้าอยากให้เร็วขึ้นอีกเท่าตัว** ย้าย Supabase ไป region `ap-southeast-1` (สิงคโปร์) ซึ่งใกล้ไทยกว่า Mumbai มาก — Supabase เปลี่ยน region ของโปรเจกต์เดิมไม่ได้ ต้องสร้างโปรเจกต์ใหม่แล้วรัน `supabase/schema.sql` ทำตอนนี้ที่ยังไม่มีข้อมูลจริงจะถูกที่สุด
